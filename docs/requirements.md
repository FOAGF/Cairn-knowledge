## 0. Summary

**Cairn** is a personal, lightweight, single-user **desktop app** for managing work **tasks** and **knowledge** together, with an **LLM assistant** that searches both.

| Area | In short |
|---|---|
| Organisation | Everything belongs to a **Category** (a built-in "General" category exists). Knowledge pages can sit in one-level **Groups** (nested groups in external knowledge mode, §5.11). |
| Tasks (§4) | Jira-like but simple. Statuses: To do / In progress / Blocked / Done / Won't do. Priority: High / Medium / Low. Labels, comments, due date, *relates to* and *parent/sub-task* links, list + board views, daily change history, and working-days / blocked-days summary for Done tasks. |
| Knowledge (§5) | Small, single-topic Markdown pages. Markdown editor with *Edit / Preview* (D-62) and LaTeX formulas (D-63), pasted images, spelling/grammar check (Harper), mentions (`#PRX-12`, `[[Page]]`), daily history, and export page as `.md`. Created manually, from a file (md/txt/pdf/docx/png/jpg; LLM drafts it, OCR is text-only) or from a task. Every new page passes a topic check, group suggestion and duplicate check. Merges are always manual, through a merge screen. A **glossary** explains work abbreviations and terms; search and the assistant use it (§5.9). |
| Assistant (§6) | Chat over tasks and knowledge with cited sources; can create/edit items after confirmation; saved conversations. Providers: **Azure AI Foundry** (Chat Completions + Responses; API key or `az login`), **Claude API**, any **OpenAI-format** endpoint, and local models (Could). Optional effort level, mapped per format. |
| Search (§7) | Hybrid keyword (SQLite FTS5) + vector search (vectors in SQLite, compared in Rust) with a built-in local **EmbeddingGemma** model. Only the top chunks go to the LLM. |
| Data (§2.1, §8.4) | One data folder; in external knowledge mode, the pages are Markdown files in a folder the user chooses (§5.11). Export/import everything (API keys excluded; in external mode, the folder's files are not included). Daily automatic backups (keep the 7 newest). |
| Languages (§8.6) | English or Simplified Chinese UI, following the system by default. English and Chinese accepted in every input. |
| Platform (§2, §9) | **Linux AppImage in v1**; Windows later (code kept cross-platform). Tauri 2 + React/TypeScript UI + Rust core (owns the DB) + bundled stateless Python sidecar (LiteLLM, ONNX embeddings, file extraction) over stdio. |
| Targets (§8) | Idle ≤ 400 MB RAM, peak ≤ 1.5 GB; window usable in ≤ 3 s; 10k pages / 20k tasks. No telemetry. |
| Out of scope (§1.4) | Teams/sharing, configurable workflows, sprints/reports/hour logging, storing original files, auto-merging, marketing or distribution (personal project, §1.5). |

## 1. Overview & goals

### 1.1 Problem
Work knowledge (how-tos, facts, decisions) and work tasks live in different places. They are hard to find again, and it is hard to ask questions across them.

### 1.2 Vision
**Cairn** (D-23): a **lightweight, personal desktop application** that combines three things, all organised by **category**:
1. **Task manager**: a simple, Jira-like tracker.
2. **Knowledge manager**: small, topic-focused Markdown pages.
3. **LLM assistant**: an assistant that can use a configurable model (especially models hosted on **Azure AI Foundry**) to answer questions, find knowledge and find tasks. It retrieves only the relevant content (via vector search) instead of sending everything to the model.

### 1.3 Goals
| ID | Goal | Status |
|---|---|---|
| G-1 | Capture knowledge quickly, including from files (PDF, image of handwriting, Markdown) with LLM help. | ✅ |
| G-2 | Keep knowledge **small and topic-specific**, and avoid duplicates. | ✅ |
| G-3 | Track tasks simply, always within a category, including key dates. | ✅ |
| G-4 | Ask natural-language questions across tasks and knowledge, at a low token cost. | ✅ |
| G-5 | Be able to switch LLM providers without code changes. | ✅ |
| G-6 | Stay **light**: low memory use while running. | ✅ |

### 1.4 Non-goals
| ID | Non-goal | Status |
|---|---|---|
| NG-1 | Team collaboration, sharing and permissions. The app is personal and single-user (D-3). | ✅ |
| NG-2 | Configurable workflows and the heavy Jira features (sprints, reports, logging hours). A simple status board and date-based duration summaries *are* in scope (see Section 4; D-3). | ✅ |
| NG-3 | Storing long documents or meeting minutes as-is. The LLM always turns an uploaded document into **exactly one** draft page (see FR-KN-DOC-1). Original files are not kept. | ✅ |
| NG-4 | Automatic merging of duplicate knowledge. Merging is manual only (D-3). | ✅ |
| NG-5 | Marketing or selling. No store listings, paid licences, onboarding for other users, or support process. The source and the releases are public as they are (D-24, D-84). | ✅ |

### 1.5 Project nature

Cairn is a **personal project**, built because the owner is interested in this field (personal knowledge management, LLM tooling, and learning Rust). It is **shared publicly as it is** (D-84): the source is on GitHub under the **MIT licence**, and releases are published there (NFR-INS-1). It is **not** marketed or sold (D-24).

What this means for implementation:
- Decisions favour **learning value and the owner's own workflow** over broad appeal. No market research, pricing or growth features are needed.
- Outside contributions go through pull requests that the owner reviews (`CONTRIBUTING.md`).
- Third-party licences are respected for redistribution: every package ships a `NOTICE` with the licences of what it contains, and the full packages carry the Gemma Terms of Use for the bundled search model; the lite packages carry no model (NFR-INS-1b).

## 3. Core concepts & data model

**Category** is the one top-level container for tasks and knowledge: what work calls a product, a project or a topic is a category in Cairn (D-2, D-61).

### 3.1 Hierarchy

```
Category                     e.g. "Product X", "General"
├── Task                     (belongs to exactly one Category)
└── Knowledge Group          e.g. "Installation", "Troubleshooting"   (optional)
    └── Knowledge Page       (belongs to exactly one Category, 0..1 Group)
```

- **Category**: the top-level container for both tasks and knowledge.
- **Knowledge Group**: a subdivision of knowledge **within a category**. The user can set it, or ask the LLM to suggest one.
- A built-in **"General"** category holds tasks and knowledge that are not specific to a category. It cannot be deleted.

### 3.2 Entities

| Entity | Key fields | Relationships |
|---|---|---|
| Category | id, name, key (short prefix, e.g. `PRX`), description, status (active/archived) | has many Tasks, Groups, Knowledge Pages |
| Task | id, key (e.g. `PRX-12`), title, description, priority, status, labels, created date, completed date, due date (optional) | belongs to 1 Category; links to other Tasks; links to Knowledge Pages; has Comments and History versions |
| Task Comment | id, text (Markdown), timestamp | belongs to 1 Task |
| Task History Version | task id, date, snapshot of task fields | belongs to 1 Task; at most one per task per day |
| Knowledge Group | id, name | belongs to 1 Category; has many Knowledge Pages |
| Knowledge Page | id, title, Markdown body, tags, origin (manual / file / task), source info (optional text), check status, created/updated | belongs to 1 Category, 0..1 Group; links to Tasks / other pages; has History versions and Attachments |
| Page Attachment | id, filename, path | an image pasted into a page body |
| Knowledge History Version | page id, date, snapshot of page fields | belongs to 1 Knowledge Page; at most one per page per day |
| Conversation | id, title, scope (categories), history budget (FR-LLM-AS-10), created/updated, messages (role, text, model, timestamp, cited items) | not linked to a category; not a knowledge source (FR-LLM-AS-5) |
| Glossary Entry | id, term, other names, short description, scope (global or one category) | global, or belongs to 1 Category; related to the entries its description names (§5.9) |

| ID | Requirement | Priority | Status |
|---|---|---|---|
| DM-1 | Every Task belongs to exactly one Category. | Must | ✅ |
| DM-2 | Every Knowledge Page belongs to exactly one Category; a page in several categories was considered and dropped (D-61). | Must | ✅ |
| DM-3 | Knowledge Pages can be organised into Groups within a Category. A group is optional. | Must | ✅ |
| DM-4 | A built-in "General" category exists and cannot be deleted. | Must | ✅ |
| DM-5 | Tasks and Knowledge Pages can be linked to each other manually, **from either side** (many-to-many). | Must | ✅ |
| DM-6 | Categories and Groups can be created, renamed and archived by the user. | Must | ✅ |
| DM-7 | Categories and Groups each have a **short description**. Descriptions are given to the LLM as context (what the category/group is about) when searching, answering and suggesting groups. Both are editable wherever the category/group is edited (D-27). | Should | ✅ |

1. **Manually** in the editor.

          Diverse-content dialog (5.5)                   Merge screen (5.6)

### 5.9 Glossary

Work notes are full of abbreviations, codes and internal names. For example, *MMU* means Mobile Manufacturing Unit, and its *auger* is the arm that delivers the explosive.

A pre-check (2026-10-15) showed that neither search nor the LLMs can be relied on to know these terms:
- The search model linked "mobile manufacturing unit" to notes that only say "MMU" only when the rest of the note gave it enough clues. Keyword search did not link them at all.
- LLMs know some industry jargon, but different models know very different amounts, and none can know internal names.

The glossary records each meaning once, and every search and every LLM prompt uses it.

| ID | Requirement | Priority | Status |
|---|---|---|---|
| FR-KN-GL-1 | A **glossary** of work terms: abbreviations, codes, internal names and trade terms. Each entry has the **term**, optional **other names** (e.g. the long form "Mobile Manufacturing Unit"), and a **short description** of a few lines that explains it (D-36). Entries have no link to a page with the full explanation, because it was tried and was not useful (D-39). | Must | ✅ |
| FR-KN-GL-2 | **Scope:** an entry is **global by default** and applies everywhere. It can instead belong to **one category**. Inside that category it **overrides** a global entry with the same term: MMU can be the explosives truck globally and the memory unit in a "Home lab" category. A term can exist once globally and once in each category (D-36). | Must | ✅ |
| FR-KN-GL-3 | **Related terms:** a glossary term named in an entry's description is linked to that entry automatically. For example, the description of *auger* says "the arm on an MMU…", so auger is linked to MMU. The link shows on both entries. It is used by search results and by the assistant (FR-LLM-AS-8). There is no separate "part of" field: naming the term in the description is enough. Related terms stay within what applies: a category entry links to its own category's entries and to global ones, and a global entry links to global ones only (D-36, D-38). | Should | ✅ |
| FR-KN-GL-4 | **Recognising a term in text.** Only whole words match. A term written in capitals matches only in capitals (`AN` does not match "an"); other terms ignore case. Codes and plurals count: `MMU-07` and `MMUs` both match MMU. Chinese terms match anywhere in Chinese text, which has no word boundaries. Other names follow the same rules. A page or task uses the global entries plus the entries of its own category. | Must | ✅ |
| FR-KN-GL-5 | **Search uses the glossary** (FR-RAG-IX-3). Glossary entries are also **searchable**: they appear in the global search and in the assistant's retrieval as their own result type. | Must | ✅ |
| FR-KN-GL-6 | **In the editor and page view**, the **first** time a recognised term appears it gets a dotted underline (later occurrences are left plain, to keep the text calm), and hovering one shows its description and scope (D-38). | FR-KN-GL-7 | **Suggested terms arise while the LLM works on sources**; there is no separate *Suggest terms* run over a page, a category or everything (D-41).
